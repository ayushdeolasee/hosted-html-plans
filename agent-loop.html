The "Review This Plan and Implement It" Loop

Architecture for pointing a coding agent at a hosted plan URL and having it review, implement, edit, and report progress back — with full version history, safe concurrent edits by multiple agents, and plans organized by repo and branch.

1. The target experience

you → claude (in the repo you want changed):

  "Review this plan and implement it:
   https://plans.<tailnet>.ts.net/p/plans-service-v1"

The agent fetches the plan, reads it as a spec, confirms it's in the right repo, asks anything genuinely ambiguous, implements phase by phase — and writes back as it goes: checking off phases, appending implementation notes, even revising sections when reality disagrees with the plan. Every write becomes a new version; the URL you reviewed always shows the latest, and the full edit history stays one click away.

2. What the loop requires

RequirementThe problemThe design answer
Fetchable The agent has to be able to reach the URL from wherever it runs. Tailnet URL for agents on your machines; share link for cloud agents (§10).
Parseable A styled HTML plan is ~40–60% CSS boilerplate by tokens, with no reliable structure to key off. A JSON meta block embedded in every plan (§6) + a ?format=text view that strips styling (§8).
Actionable "Implement this" is meaningless without knowing which repo/branch and what "done" means. First-class repo + branch tags on every plan (§7) and per-phase acceptance criteria in the meta block (§6).
Writable by agents A read-only plan is stale the moment work starts; agents must be able to update, append, and revise — sometimes two at once. Open writes on the private listeners; every write creates an immutable new version (§4); conflict-free write primitives for concurrent agents (§5).

4. Living documents: edits & version history core feature

Plans are append-only stacks of immutable versions. Nothing is ever overwritten or lost:

  • Every write creates version N+1. Create, full revision, append, or a meta/status update — each lands as a complete new snapshot of the document. The server assigns version numbers under a per-plan lock, so they're always a clean 1, 2, 3…
  • Anyone can write. Per your call: no tokens, no ownership — any agent or person on the LAN or tailnet can update any plan. The history is the safety net: a bad edit is a one-click restore, never a loss. (The public share listener remains read-only — internet visitors can never write. §10.)
  • URLs identify plan + version:
    URLServes
    /p/my-featureLatest version — the default link, always current. This is what you bookmark and what you hand to agents.
    /p/my-feature?version=3Exactly version 3, forever. The server injects a slim banner — "Viewing v3 of 7 · jump to latest" — so a historical page is never mistaken for current.
    /p/my-feature?version=3&diff=2 laterOptional nicety: highlight what changed between two versions.
  • History is browsable — GET /api/plans/{slug}/history returns the version list: number, timestamp, author (?agent= on the write), action (create / revise / append / status), and an optional one-line note (like a commit message — the skills always supply one). The homepage shows this as a per-plan "History" panel with view + restore buttons. Restore just copies vN as a new latest version — even restores are history.
  • Storage stays dumb: files/<slug>/v0001.html, v0002.html… with per-version metadata in index.json. Plans are small (tens of KB), so even hundreds of versions round to nothing; a size cap per plan (default 50 MB) guards the pathological case. Delete becomes archive: deleting from the homepage moves the plan folder to trash/ (purge-on-demand from a trash view) — consistent with "never lose a version".
Concept: immutable versions. This is the same idea as git commits or CRDT-free event logs: writers only ever add states, never mutate them. It buys three things at once — history for free, trivially safe concurrent writes (two writers produce v5 and v6 rather than corrupting one file), and idempotent storage code (a version file is written once with an atomic rename and never touched again).

5. Two agents, one plan concurrency design

Two agents will sometimes write the same plan at the same time — a planner revising phase 4's description while an implementer checks off phase 2. The design makes the common cases conflict-free by construction and the rare case explicit:

Write primitiveSemanticsConflict behavior
POST /api/plans/{slug}/append Body = an HTML fragment; the server inserts it at the end of the document (before </main>) and snapshots a new version. Used for implementation notes, deviation logs, per-phase reports. Never conflicts. The server serializes appends under the plan lock; two simultaneous appends land as two consecutive versions, both preserved in order.
POST /api/plans/{slug}/status Body = a partial meta update ({"phases":[{"id":2,"status":"done"}]}). The server merges it into the current meta block and snapshots a new version. Never conflicts unless two writers touch the same field, in which case last-write-wins — and both values remain visible in history.
PUT /api/plans/{slug} Full document replacement (structural rewrites). The writer sends base_version=N — "I edited from version N." Optimistic locking: if latest ≠ N, the server rejects with 409 + the current version; the agent re-fetches, re-applies its changes, retries. Skills encode this retry automatically. If a writer omits base_version, the write is accepted and the version is flagged forced in history.
Why this shape? It mirrors how databases and git handle the same problem: cheap operations are made commutative (appends and field-level merges can interleave in any order), and only whole-document rewrites need coordination (compare-and-swap on the version number). Since 95% of implementer traffic is "tick a phase, append a note," two agents can hammer the same plan all day and never see a 409. And because every write is an immutable version, even a genuinely bad merge is inspectable and reversible in history rather than silently lost.

6. Machine-readable plans a convention, not code

Every plan an agent authors embeds one <script type="application/json" id="plan-meta"> block. Browsers ignore it (invisible to you); agents parse it first and treat the prose as elaboration:

<script type="application/json" id="plan-meta">
{
  "kind": "implementation-plan",
  "version": 1,
  "status": "approved",              // draft | approved | in-progress | done
  "repo": "github.com/ayushdeolasee/hosted-html-plans",   // ← also indexed as a tag
  "branch": "main",                                        // ← also indexed as a tag
  "workdir_hint": "~/Developer/hosted-html-plans",
  "phases": [
    { "id": 1, "title": "Core server",  "status": "done",
      "accept": "curl push + GET round-trips a file locally" },
    { "id": 2, "title": "Homepage",     "status": "in-progress",
      "accept": "list/open/delete/rename/search work in browser" }
  ],
  "constraints": [
    "no Docker", "funnel strictly on-demand", "minimal RAM/CPU"
  ]
}
</script>
  • Per-phase accept criteria convert "implement this" into a verifiable checklist, written when the planner has full context.
  • constraints carries the non-negotiables so they survive the handoff even if the implementer skims the prose.
  • repo / branch do double duty: targeting (the implementer refuses gracefully on mismatch) and organization (§7). The authoring skill fills them automatically from git remote get-url origin and git branch --show-current — the agent never has to remember.
  • On every push the server extracts this block into the index, which is what makes filtering, grouping, and status badges possible without opening files.

7. Organization: repo → branch automatic

Plans are categorized by two first-class tags, repo and branch, set automatically at creation:

  • Agents self-tag. The authoring skill reads the git context it's sitting in and stamps repo + branch into the meta block (equivalently, ?repo=&branch= params on push). Plans created outside any repo — research reports, roadmaps — land untagged in a General group.
  • The homepage groups by repo, then branch: a sidebar of repos with plan counts; within a repo, branch sections (worktree-friendly — you work multi-branch constantly). Filter chips + search combine.
  • The same resources are open to agents — the homepage has no private API. Anything you can see, an agent can query: 
    # "what plans exist for the repo/branch I'm standing in?"
GET /api/plans?repo=github.com/ayushdeolasee/hosted-html-plans&branch=main

# the implement-plan skill runs this automatically at session start, so
# "implement the plan for this branch" works with NO url pasted at all —
# and the authoring skill uses it to update an existing plan instead of
# creating a near-duplicate.

That last point quietly upgrades the target experience: once tagging exists, "review the plan for this branch and implement it" is enough — the agent discovers the URL itself.

8. The write/read API consolidated

EndpointWhat it does
POST /api/plansCreate (or new version if slug exists). Params: ?slug=&title=&agent=&repo=&branch=&note=. Returns id, slug, version, URLs.
PUT /api/plans/{slug}Full revision; base_version for optimistic locking (§5).
POST /api/plans/{slug}/appendConflict-free append of an HTML fragment (§5).
POST /api/plans/{slug}/statusConflict-free meta merge — phase ticks, status flips (§5).
GET /p/{slug}Latest version. ?version=N for history (with banner); ?format=text for the style-stripped agent view (~half the tokens); combinable.
GET /api/plansList + filters: ?repo=&branch=&status=&q=.
GET /api/plans/{slug}One plan's metadata: latest version, parsed meta, tags, share state.
GET /api/plans/{slug}/historyVersion list: number, time, author, action, note.
POST /api/plans/{slug}/restore?version=NCopy vN forward as the new latest (restores are versions too).
DELETE /api/plans/{slug}Archive to trash (recoverable); purge only from the homepage trash view.
POST /api/plans/{slug}/share · DELETE …/sharePublic share on/off — unchanged from the main plan; still opens/closes the funnel listener on demand.

All write endpoints exist only on the private listeners (LAN + tailnet). The funnel listener still serves exactly one route: GET /share/{token} — which always serves the plan's latest version.

9. The two skills

Authoring side: push-plan skill

When a planning session produces an HTML plan: embed the meta block; auto-fill repo/branch from git context; check for an existing plan for this repo+branch first and offer to revise it (PUT) rather than spawn a duplicate; push with a one-line version note; hand you the tailnet URL.

Implementing side: implement-plan skill

Triggered by "review/implement this plan <url>" — or with no URL at all, via repo/branch discovery (§7). The protocol:

  1. Fetch ?format=text; note the version number it read (its base_version for any structural edit).
  2. Review first, genuinely — a gate, not a summary: does the plan match this repo's reality? Contradictions, stale assumptions, missing pieces? Proceed only when resolved or waved off.
  3. Verify targeting — meta repo/branch vs. actual git remote/branch; stop with a clear message on mismatch.
  4. Implement phase by phase, checking each accept criterion before moving on.
  5. Write back continuously — status tick + append note after each phase; a PUT (with base_version, retrying on 409) only when the plan itself needs revising. Every write carries a note.

11. Why not just use git for this?

Plans servicePlan files in each repo
One URL works from any machine/worktree✅❌ path differs per checkout; wrong-worktree confusion
Readable on your phone / shareable to others✅ tailnet / share link❌ needs a checkout or GitHub rendering (strips styling)
Cross-repo & non-code plans✅❌ homeless
Progress updates without commit noise✅ re-push❌ every status tick is a commit
Edit history✅ built-in versions (§4)✅ commits
Survives in repo history / reviewable in PRs❌✅

Verdict: the service is the working medium; git is the archive. The implementer skill can optionally commit a final snapshot of the finished plan into the repo (docs/plans/) when work completes — off by default, --archive flag.
