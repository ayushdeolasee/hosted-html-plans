Hosted HTML Plans — Implementation Plan

A single native binary — no Docker — that runs as a background service on macOS or Linux. Agents push HTML plans to it; you view them over LAN, Tailscale, or on-demand public share links, and manage them from a built-in homepage.

1. What we're building

One program, plans, that does everything:

  • An HTTP server that accepts HTML files via a simple authenticated API, stores them as plain files under your home directory, and serves them back as real pages.
  • A homepage at / — lists every plan with title, date, and source; open, delete, rename, search, and a per-plan share button for public links.
  • Tailscale built in — the binary embeds Tailscale as a library (tsnet), so the service joins your tailnet as its own device named plans with automatic HTTPS. No Tailscale install required on the box, no interference with any existing Tailscale setup. The public funnel is off by default and exists only while at least one plan is explicitly shared.
  • Self-installing service management — plans service install registers it with launchd (macOS) or systemd (Linux) so it starts at boot and restarts on failure.
  • A push integration for agents — a tiny CLI script plus a Claude Code skill so any agent can run one command and get back a viewable URL.

Dropping Docker removes the Docker daemon (easily 100+ MB of RAM by itself), the sidecar container, volumes, and compose files. Deployment becomes: copy one binary, run one install command.

Three listeners inside one process, each mapped to an access mode:

  • Plain TCP :8080 — the full app, for LAN access.
  • tsnet :443 — the full app, tailnet-only, with automatic TLS as plans.<tailnet>.ts.net.
  • tsnet funnel :8443 — the shares-only router. This listener is created when you share your first plan and closed when you revoke the last one. When it doesn't exist, the box has zero public exposure.
Concept: tsnet. Tailscale publishes its client as a Go library. Instead of talking to a Tailscale daemon on the machine, the plans binary contains one: it joins your tailnet as its own node, gets its own 100.x address, its own name, and its own HTTPS certificate — all in-process, storing its keys in the data directory. This is how apps like Golink and Headscale-adjacent tools work. Two practical wins for us: it behaves identically on macOS and Linux, and funnel becomes a plain Go listener (ListenFunnel) we can open and close programmatically — which is exactly the on-demand semantics you asked for.

3. The three access modes

ModeURLWho can reach itHow
Direct IP http://<box-LAN-ip>:8080 Anyone on your home LAN Ordinary TCP listener. Works with zero Tailscale setup — also the dev/fallback mode. Can be restricted to localhost or disabled in config.
Tailnet https://plans.<tailnet>.ts.net Only devices on your tailnet Embedded tsnet node with automatic Let's Encrypt TLS. Always on once authenticated. This is the primary way you'll use it — from your Mac, phone, anywhere.
Public share on-demand only https://plans.<tailnet>.ts.net:8443/share/<token> Anyone with the link Created only when you click Share on a plan: the app opens a funnel listener bound to the shares-only router, and closes it when the last share is revoked. See §4.
Concept: tailnet vs. funnel. Tailnet traffic (serve-style) never leaves your WireGuard mesh — only your own devices can connect. Funnel relays traffic from the public internet through Tailscale's edge servers to the node. Funnel only supports ports 443, 8443, and 10000; our tailnet listener owns 443, so shares go on 8443. Funnel must be permitted once for this node in your tailnet's ACL policy ("funnel" node attribute) — permitting it exposes nothing by itself; nothing is reachable until the app actually opens the funnel listener.

4. On-demand public sharing

The funnel is never a standing configuration — it's a listener whose lifetime is tied to the share button:

  1. Idle state (default): no funnel listener exists. The box has zero public-internet exposure; only the LAN and tailnet listeners are open.
  2. You click Share on a plan: the app generates a 128-bit random token, stores it, and calls tsnet.ListenFunnel("tcp", ":8443") to open the public listener (bound to the shares-only router). You get the public URL on your clipboard.
  3. More shares: the listener is already open; each share is just a new token. A visible banner on the homepage says "Public sharing active · N plans" the whole time.
  4. You revoke the last share (or delete the last shared plan): the app closes the funnel listener. Back to zero exposure.
  5. Restart resilience: on startup the app opens the funnel listener if and only if active shares exist in index.json.

Because the funnel listener serves a dedicated router with exactly one route (/share/<token>), the homepage, API, and unshared plans are physically unreachable from the internet even while sharing is active.

5. Running as a background service

The binary manages its own installation — no hand-written unit files:

# on the box (or any Mac/Linux machine)
plans service install     # writes + enables launchd plist or systemd unit, starts it
plans service status      # running? which listeners? tailnet auth state? funnel on?
plans service uninstall   # stop + remove the service registration
plans run                 # foreground mode, for development and debugging
OSMechanismDetails
macOS launchd LaunchAgent
~/Library/LaunchAgents/com.ayushdeolasee.plans.plist		 KeepAlive restarts it on crash; RunAtLoad starts it at login. Logs to ~/Library/Logs/plans.log.
Linux systemd system unit
/etc/systemd/system/plans.service		 System-level (not --user) so it runs on a headless box without anyone logged in. Restart=on-failure; logs go to the journal (journalctl -u plans). Runs as your user, not root. --user flag available if preferred.

First-run flow

  1. plans service install generates a config with a random API token at ~/.config/plans/config.json and starts the service. LAN mode works immediately.
  2. The log (and plans service status) prints a Tailscale auth URL once — you open it, approve the new plans node in your tailnet, done. tsnet stores its keys in the data dir and never asks again.

Concept: launchd vs. systemd. Both are the OS's init/supervisor: they start your process at boot/login, restart it if it dies, and capture its output — the same job Docker's restart: unless-stopped was doing, but with zero daemon overhead. launchd reads XML "plists"; systemd reads INI-style "units". Our install command just writes the right file for the OS it's on and loads it — the templates live in the repo so you can read exactly what gets installed.

6. Stack decisions

DecisionChoiceWhy
Language / framework Go, stdlib net/http — no framework One static binary per OS/arch, cross-compiled from your Mac (GOOS=linux GOARCH=amd64 go build). ~0% idle CPU, instant start, and it's the only mainstream option where Tailscale embeds as a library (tsnet is Go-only) — which is what makes the no-Docker, no-sidecar design possible at all.
Tailscale integration Embedded tsnet node named plans No dependency on host Tailscale; identical on macOS/Linux; funnel is a programmatic listener (perfect for on-demand). Alternative — reusing the host's tailscaled — costs less RAM but couples to host config, shares the host's node name, and behaves differently between the macOS app and Linux daemon. See §14.
Metadata store One index.json file, mutex-guarded, atomic writes No database engine. At personal scale (hundreds of plans, single writer) a JSON index is lighter and trivially inspectable — cat index.json is the admin tool.
HTML storage Flat files, versioned: <data-dir>/files/<slug>/v0001.html, v0002.html… Plans stay ordinary files in your home directory — grep them, back them up with everything else. Every edit is an immutable new version; /p/<slug> serves the latest, ?version=N serves history (full design in agent-loop.html).
Homepage UI One HTML template + one vanilla-JS file, compiled in via go:embed No build step, no node_modules, no runtime file dependencies — the binary is fully self-contained. Theme-aware, styled like this document.
Auth None — open reads and writes on the private listeners (LAN + tailnet) Your call: any agent or person who can reach the service can push and edit. Reachability is the auth boundary, and full version history (see agent-loop.html) makes every write recoverable. The public funnel listener stays read-only. No tokens to generate, store, or leak.
Service supervision Native launchd / systemd via plans service install Replaces everything Docker was providing (start at boot, restart on crash, log capture) with the OS's own supervisor and zero extra processes.

7. Resource budget

ConfigurationRAM (idle)CPU (idle)Disk
plans with tsnet connected (normal)~40–60 MB≈0% (WireGuard keepalives)one ~25 MB binary + your plans
plans with Tailscale disabled in config (LAN-only)~10 MB≈0%same
For comparison, the Docker design: dockerd (~100+ MB) + sidecar container (~50 MB) + app container. Going native cuts total footprint by well over half, to a single process.
  • tsnet is most of the binary size and RAM — it's a full Tailscale client. That cost buys modes 2 and 3; the HTTP server itself is a rounding error.
  • No background work: no polling loops, no cron, no thumbnailing, no file watchers. The process sleeps until a request arrives.
  • On Linux the unit sets MemoryMax=128M and CPUQuota=50% as a hard backstop, mirroring what compose limits did.
  • Logging is request-line only at default verbosity; macOS log file is size-capped by a built-in rotate-on-startup check.

8. API design

EndpointAuthWhat it does
POST /api/plans—Body = raw HTML (or multipart). Optional ?title=, ?slug=, ?agent=. Title auto-extracted from <title> if not given. Returns JSON with id, slug, and ready-to-open URLs for LAN and tailnet.
GET /api/plans—List all plans with metadata (JSON). Powers the homepage and lets agents check what exists.
GET /p/{slug}—Serve the plan HTML itself.
PATCH /api/plans/{id}—Rename / edit title.
DELETE /api/plans/{id}—Archive to trash (recoverable; purge from the homepage trash view). If it was the last shared plan, the funnel listener closes as a side effect.
POST /api/plans/{id}/share—Generate a share token, open the funnel listener if it wasn't open, return the public URL.
DELETE /api/plans/{id}/share—Revoke the share (link 404s immediately); close the funnel listener if this was the last active share.
GET /share/{token}—Serve a shared plan. The only route on the funnel listener's router; also available on the private listeners.
GET /healthz—Liveness check; plans service status uses it.

This is the core surface. The agent-collaboration layer adds versioned writes (PUT, append, status, history, restore), ?version=N / ?format=text views, and repo/branch filters — consolidated table in agent-loop.html §8.

9. Management homepage

  • List view — every plan as a row/card: title, slug, source agent, upload date, size. Newest first, with client-side search-as-you-type.
  • Open — click opens the plan in a new tab (links are mode-aware: the page links to whichever host you loaded it from, so LAN links stay LAN and tailnet links stay tailnet).
  • Delete — with a confirm step.
  • Rename — inline title edit.
  • Share button — per plan. One click creates the token, opens the funnel if needed, and copies the public link; a badge marks shared plans; one click revokes. A persistent banner shows whenever public sharing is active, with a "revoke all" shortcut.
  • Copy link — copies the tailnet URL for pasting into notes/messages to yourself.
  • Same visual language as this document: theme-aware (light/dark via prefers-color-scheme), no external assets, works on your phone.

10. Agent integration

Three layers so it works everywhere:

  1. push-plan script (in the repo, symlink to ~/bin) — push-plan file.html [title]: reads PLANS_URL from ~/.config/plans/config.json (no token — writes are open on trusted networks), auto-tags repo + branch from the git context it runs in, pushes, prints the URLs, and copies the tailnet URL to the clipboard when run on your Mac.
  2. Claude Code skill (~/.claude/skills/push-plan/) — so any session can be told "push this to plans" and the model knows the exact command and where credentials live. Agents never share plans publicly — the share button is human-only by convention, and the skill says so.
  3. Global CLAUDE.md snippet — a short addition to your existing "Deliverables: HTML, not Markdown" section telling agents: after writing an HTML deliverable, push it with push-plan and give you the returned URL instead of (or alongside) the local path. This is what makes it automatic across all future sessions.

11. Security model worth reading

  • All access — read and write — is gated by network reachability (LAN or tailnet), not credentials. Any agent or person on a trusted network can push and edit any plan; full version history makes every write recoverable, and "delete" only archives to trash. No tokens anywhere.
  • Default public exposure is zero — not "closed" but nonexistent: the funnel listener isn't open. While sharing is active, the public side reaches a router whose only route is /share/<token>. Tokens are 128-bit random URL-safe strings: unguessable, individually revocable.
  • Plan HTML is served as-is (it's your own agents' output, and plans need their inline CSS/JS to work). Shared pages get a Content-Security-Policy blocking external network calls as a courtesy hardening step.
  • The service runs as your user, unprivileged — no root, no Docker socket, and ports 8080/8443 need no elevated permissions (tsnet's 443 terminates inside the tailnet, not on a host port).
  • Caveat to flag honestly: anyone on the LAN can read plans over plain HTTP in mode 1. If the box sits on your home network, that's fine; if that ever changes, set "lan_listen": "off" (or "127.0.0.1:8080") in config and the service becomes tailnet-only.

13. Build phases

1

Core server testable locally

Go server: push API, JSON-index storage, plan serving, LAN listener, config + data-dir handling. Run with plans run on your Mac, verify end-to-end with curl.

2

Management homepage

List / open / delete / rename / search / copy-link UI (share button lands in phase 5). Verified in the browser against the local server.

3

Service management + deploy access mode 1

plans service install/uninstall/status for launchd and systemd. Cross-compile, copy the binary to the box, install, confirm http://<box-ip>:8080 from your Mac and that it survives a reboot. Record actual RAM/CPU against §7.

4

tsnet tailnet mode access mode 2

Embed the tsnet node; first-run auth-URL flow (needs your hands once, ~a minute in the Tailscale admin console). Confirm https://plans.<tailnet>.ts.net from your phone off-LAN.

5

On-demand funnel shares access mode 3

Permit funnel in your tailnet policy (one-time checklist), build the listener open/close + share button + reconcile-on-startup, then verify the full lifecycle: share → link opens from a device on neither LAN nor tailnet → revoke → link dead and listener confirmed closed.

6

Agent integration

push-plan script, the Claude Code skill, and the CLAUDE.md snippet. Final test: an agent writes a plan, pushes it, hands you a working tailnet URL.
